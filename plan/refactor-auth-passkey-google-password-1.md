# Introduction

![Status: Planned](https://img.shields.io/badge/status-Planned-blue)

This is the implementation guide for the agreed authentication rework. Passkeys remain preferred, Google remains a complete alternative, and password access restores compatibility for users without an accessible passkey provider or Google account. Password authentication requires an authenticator-app code when TOTP is enrolled; otherwise it requires a code sent to the verified account email.

Use `docs/design/assets/themis-sign-in.html` as the visual reference instead of starting another independent design exploration. Keep the familiar form, separate sign-in from account creation, and never require a failed passkey attempt before showing either path.

This plan supersedes the passwordless-only product direction in `plan/refactor-passwordless-identity-federated-fallback-1.md` and `docs/specs/2026-09-01-auth-passwordless-identity/` where they conflict. Their completed security work remains relevant. Do not treat historical completion marks as evidence for this plan. No application implementation, migration, or acceptance testing has been performed by authoring this document.

## 1. Requirements & Constraints

### Product Contract

- **REQ-001**: Offer passkey, Google, and password sign-in. Prefer passkey visually without requiring it for Google or password users.
- **REQ-002**: Google authentication establishes a full session without mandatory local TOTP, email challenge, or passkey enrollment.
- **REQ-003**: Valid password proof never establishes a full session. The server selects `totp` if confirmed enrollment exists and `email` otherwise. The client cannot override that choice.
- **REQ-004**: Failed, cancelled, expired, unavailable, or undecryptable TOTP is not equivalent to absent enrollment. Never offer automatic email fallback for an enrolled account.
- **REQ-005**: A linked authenticator means a confirmed TOTP enrollment, not a remembered browser, pending setup, or passkey.
- **REQ-006**: Existing users may add methods after appropriate fresh authentication. Offering three methods does not automatically configure all three on each account.
- **REQ-007**: One global user can have multiple active passkeys, one password credential, a confirmed TOTP enrollment, and a linked Google identity. Preserve tenant memberships and credential-bound account selection.
- **REQ-008**: Provide separate sign-in, sign-up, password-reset, and recovery intentions. Keep `/app/{locale}/auth/identity` as the current sign-in entry; add explicit localized routes for the other intentions rather than changing the public entry unnecessarily.
- **REQ-009**: New-device users can use a registered passkey from any accessible provider, linked Google, or configured password plus the required code. A new unregistered passkey cannot identify an existing user.
- **REQ-010**: TOTP enrollment is optional. Password users without enrollment can use email verification indefinitely; do not force an authenticator setup wizard.
- **REQ-011**: Support Firefox on Linux without a passkey manager through password plus email/TOTP and Google when configured. Do not require a browser switch, extension, phone QR flow, or security key to use password authentication.
- **REQ-012**: Password reset changes only a configured password. It must not silently add a password to a passkey/Google-only account or remove TOTP.

### Security Contract

- **SEC-001**: Describe password plus email as email-based two-step verification, not phishing-resistant MFA or a claim of NIST AAL2 compliance. Email does not guarantee an independent factor, particularly when it is also the password-reset channel.
- **SEC-002**: Passkey authentication requires server-verified user verification, RP ID, origin, challenge, active credential status, and account binding. It needs no extra local code for ordinary access.
- **SEC-003**: Google access is an explicitly trusted federated policy, not proof that Google performed MFA. Verify signature, issuer, audience, expiry, nonce, and verified email server-side. Keep identity keyed by `(issuer, subject)` and never auto-link by email.
- **SEC-004**: Pending password verification is not a Passport-authenticated restricted user. It grants neither product access nor enrollment authority. Audit all middleware callers, including API keys, activation, and realtime authorization.
- **SEC-005**: Challenges are purpose-specific, short-lived, session-bound, attempt-limited, and atomically consumed. Email bootstrap, password second step, password reset, email recovery, and credential management cannot exchange challenges.
- **SEC-006**: Recheck credential/security versions and current TOTP enrollment at challenge completion. Reject stale password proof after reset, factor change, account disablement, or security-version increment. An email challenge issued before TOTP activation becomes invalid.
- **SEC-007**: Use shared Redis-backed abuse limits, not only process-local maps. Apply per-flow, per-normalized-identifier HMAC, and per-IP limits. Fail closed on security limiter failure; return a recoverable service-unavailable response.
- **SEC-008**: Protect state-changing routes with the existing CSRF/origin policy and secure session cookies. Rotate session IDs on entry into pending authentication and on final login; bind challenges to the resulting session. Reject open redirects.
- **SEC-009**: Never log passwords, OTPs, TOTP secrets, reset tokens, recovery codes, Google ID tokens, credential payloads, or authorization URLs. Audit method, factor, outcome, user/account IDs when known, and coarse request context only.
- **SEC-010**: TOTP secrets need authenticated encryption with versioned keys distinct from session/OTP secrets. Store recovery codes and reset tokens as hashes; keep OTP verification hashes keyed because six-digit codes have a small search space.
- **SEC-011**: Method addition/removal, TOTP replacement/disable, recovery-code regeneration, and email changes require recent explicit authentication bound to the operation. A full session alone is insufficient. A TOTP-enrolled password user must prove TOTP or a recovery code; linked Google or an active UV passkey can independently authorize these changes under the agreed policy.
- **SEC-012**: Email-only passkey recovery must not bypass enrolled TOTP. For enrolled users require an active UV passkey, linked Google, or password plus a recovery code before granting replacement-credential authority. Do not add an email-only TOTP-reset endpoint.
- **SEC-013**: Keep existing pending-passkey registration plus verification assertions until separately reviewed. Do not silently remove the second ceremony as a visual simplification.
- **SEC-014**: A device cookie does not bypass the password second step in this release. Disable any historical remembered-device bypass on the new branch.
- **SEC-015**: Change/reset password, TOTP replacement/disable, and lost-credential recovery increment the user's security version and invalidate affected sessions and outstanding grants. Apply checks on session deserialization and realtime use, not only in Angular guards.

### Implementation Defaults

These are explicit implementation defaults, not measurements of the existing runtime. Represent them in validated configuration in `libs/shared/src/lib/env.ts`; expose only relevant expiry/cooldown timestamps to the client.

| ID      | Setting                           | Default and behavior                                                                                                                                                                                                                                        |
| ------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CFG-001 | Password policy                   | 15 to 128 Unicode code points; permit spaces/paste/autofill; no mandatory character classes, trimming, silent truncation, or periodic rotation. Apply the same documented NFC normalization on creation and verification for new hashes only.               |
| CFG-002 | Password hashing                  | Argon2id, 19,456 KiB memory, 2 iterations, parallelism 1, unique random salt of at least 16 bytes. Benchmark on the deployment runtime before release; never silently reduce below this baseline. Store PHC format.                                         |
| CFG-003 | Pending login lifetime            | 10 minutes from successful password proof; factor resends cannot extend it.                                                                                                                                                                                 |
| CFG-004 | Email code                        | Cryptographically random 6 digits, 5-minute lifetime capped by the pending-flow expiry; 5 failed verification attempts per flow. Resend supersedes the previous code without resetting attempts.                                                            |
| CFG-005 | Email delivery limits             | 60-second cooldown; at most 5 sends per identifier per 15 minutes and 20 sends per IP per 15 minutes across auth purposes. Server returns `resendAvailableAt`; no client-invented countdown authority.                                                      |
| CFG-006 | Password attempt limits           | 10 attempts per identifier per 15 minutes and 50 per IP per 15 minutes, including unknown users. Generic credential failure; perform dummy password verification for absent credentials.                                                                    |
| CFG-007 | TOTP                              | RFC 6238, SHA-1 for broad authenticator compatibility, 6 digits, 30-second step, tolerance of one adjacent step. Atomically reject reuse of an already accepted step per enrollment. Five failed attempts per pending flow plus 10 per user per 15 minutes. |
| CFG-008 | TOTP setup                        | Pending encrypted secret expires in 10 minutes; replace pending setup on restart. Activate only after a correct code. Preserve an existing active enrollment until replacement confirmation succeeds.                                                       |
| CFG-009 | Recovery codes                    | 10 codes with at least 128 random bits each; display once, allow download/copy, store hashes, consume atomically. Regeneration invalidates previous codes.                                                                                                  |
| CFG-010 | Password reset                    | 32 random bytes, 15-minute expiry, single use, browser-bound exchange before mutation. No automatic full login after resetting. Use normal password plus required second-step sign-in afterward.                                                            |
| CFG-011 | Sensitive-operation authorization | 5-minute, purpose-bound, single-use grant obtained through explicit reauthentication. Do not infer permission solely from a general `authenticatedAt`.                                                                                                      |
| CFG-012 | User version                      | Add non-null `authVersion` default 1. Snapshot in pending flows and sessions and compare with the current user record.                                                                                                                                      |

Use a locally deployed compromised/common-password blocklist without sending plaintext passwords to external services. Phase 1 must record the licensed dataset, checksum, update process, and packaging location; production password enablement is blocked until the artifact is present. Do not ship a short hardcoded example list as production protection.

### UX Contract

- **UXD-001**: Adapt the reference template's outside logo, compact single-column card, left-aligned heading, and conventional form. Use current Manrope/Inter and zinc surface tokens, not the historical CDN configuration or custom palette.
- **UXD-002**: Sign-in order is passkey, official Google button when enabled, a single password divider, email/password fields, forgot-password link, password submit, and create-account footer. Passkey is the primary emphasis; do not make all three methods primary buttons.
- **UXD-003**: Use `autocomplete="username webauthn"` and `current-password` on sign-in with conditional passkey autofill only where supported. Keep explicit passkey access; feature detection is not evidence that the user has no credentials. Do not open a modal passkey ceremony on page load.
- **UXD-004**: Render Google once, not a button that reveals a second button. Use its SDK-supported branding. Handle SDK blocked, missing configuration, cancellation, and asynchronous completion errors without removing password access.
- **UXD-005**: A cancelled ceremony keeps the sign-in form and entered email. Show neutral inline guidance; do not assert that the user has no account or redirect to sign-up.
- **UXD-006**: After password proof show one server-selected code screen: `Check your email` with masked destination and resend controls, or `Enter your authenticator code` with a recovery-code action. Never offer email as an alternative on the TOTP screen.
- **UXD-007**: Use one accessible input for each code, supporting paste, leading zeros, and `autocomplete="one-time-code"`; avoid independent single-digit inputs. Distinguish incomplete, incorrect, expired, rate-limited, and service-unavailable states.
- **UXD-008**: Sign-up provides a passkey-preferred choice, Google, and password creation without trying an existing passkey first. Password sign-up is email/password submission, email confirmation, then full session after both proofs are validated and bound; this confirmation satisfies the initial email second step, so do not send two consecutive email codes. Do not require TOTP setup.
- **UXD-009**: Use explicit back/edit actions and browser-safe state restoration. Keep passwords/codes/secrets out of URLs, localStorage, and sessionStorage; clear sensitive form values after submission/exit. Restore only opaque flow state through the session-bound API.
- **UXD-010**: Preserve a validated same-origin localized return path through every method and verification step. Keep workspace activation separate from authentication and preserve its existing completion/skip behavior.
- **UXD-011**: Omit Remember me, automatic One Tap, adaptive method ordering, SMS, and automatic passkey upgrades from this release. No new marketing panel or global design-system rework.
- **UXD-012**: Meet WCAG AA; visible focus, explicit labels, password visibility control with accessible name, touched/submitted errors, heading focus after transitions, non-disruptive live status, reduced motion, and no horizontal overflow at 320 px. Test 360/768/1440 px, light/dark, and mobile keyboard behavior.

### State And API Contract

The following names and endpoints are proposed unless marked existing. Implement Zod request/response schemas and OpenAPI documentation before clients. Keep the established response envelope.

| State                            | Event                                                | Server result / UI result                                                                                                                                                             |
| -------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `anonymous`                      | Valid active UV passkey                              | Rotate session, set full authority and method `passkey`, resolve credential-bound membership, redirect.                                                                               |
| `anonymous`                      | Valid linked/new Google identity                     | Rotate session, set full authority and method `google`, resolve membership, redirect. Matching email without a link returns controlled linking guidance, not account merge.           |
| `anonymous`                      | Correct password, no active TOTP                     | Create non-authenticated pending flow with method `password`, required factor `email`, credential/auth versions and expiry; deliver code to the verified stored email.                |
| `anonymous`                      | Correct password, active TOTP                        | Create non-authenticated pending flow with required factor `totp`; send no email code.                                                                                                |
| `pending_email` / `pending_totp` | Correct required code, current versions              | Atomically consume proof, rotate session, issue full authority with method `password` and second factor `email` / `totp`.                                                             |
| `pending_totp`                   | Correct unused recovery code                         | Consume code and pending proof; full session with second factor `recovery_code`; notify user and recommend replacing lost authenticator. Do not silently disable TOTP.                |
| Any pending state                | Expiry, version mismatch, attempt exhaustion, cancel | Terminal flow; no product/enrollment authority; clear pending state and offer safe restart.                                                                                           |
| `signup_pending_email`           | Correct signup code                                  | Atomically create verified user, password credential and account/membership, consume password/email proof, issue full session. Existing-email collisions never overwrite credentials. |
| `password_reset`                 | Valid reset token and new password                   | Change configured password, increment auth version, invalidate sessions/grants; sign-in required. Keep enrolled TOTP.                                                                 |
| `full`                           | Sensitive method change                              | Require explicit purpose-bound reauthentication, mutate atomically, invalidate affected authority, notify and audit.                                                                  |

| Route                                                                     | Purpose and authority                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------- |
| Existing `POST /api/auth/identity/start`, `GET /api/auth/identity/status` | Extend resumable browser-bound state for new intentions. Never expose another session's email/user or secrets.                                                                                                                         |
| Existing passkey routes and `POST /api/auth/google/complete`              | Preserve credential verification, integrate consistent session completion and durable method metadata.                                                                                                                                 |
| `POST /api/auth/password/sign-in`                                         | `{ email, password }`; returns pending `{ flowId, requiredFactor, expiresAt, resendAvailableAt?, maskedEmail? }` only after valid password. No account-existence disclosure before proof.                                              |
| `POST /api/auth/password/verify`                                          | `{ flowId, code, kind: 'email'                                                                                                                                                                                                         | 'totp' | 'recovery_code' }`; server accepts only its selected factor or explicitly allowed recovery-code branch. |
| `POST /api/auth/password/resend`                                          | `{ flowId }`; valid email-factor flow only, server-owned destination. No TOTP downgrade or arbitrary email parameter.                                                                                                                  |
| `POST /api/auth/password/sign-up`, `/sign-up/verify`, `/sign-up/resend`   | Pending password hash plus email challenge; generic start response; no usable user session until confirmation. Require a new email verification before resolving existing-email guidance.                                              |
| `POST /api/auth/password/reset/request`, `/reset/complete`                | Generic request response for absent/unconfigured users. Exchange hashed token into a short-lived browser-bound reset grant before final mutation; do not consume merely on link preview/GET.                                           |
| `POST /api/auth/reauth/start`, `/reauth/complete`                         | Purpose-bound authorization using active UV passkey, linked Google, or password plus current factor. Reuse challenge logic without granting a general login before completion.                                                         |
| `POST /api/auth/totp/setup`, `/confirm`, `/disable`                       | Fresh operation grant; setup returns secret/otpauth URI once with `Cache-Control: no-store`; confirm activates and returns new recovery codes once. Disable requires a verified alternative password/email path or independent method. |
| `POST /api/auth/recovery-codes/regenerate`                                | Fresh operation grant; atomically replace hashed codes and return plaintext once.                                                                                                                                                      |
| `POST /api/auth/password/set`, `/change`, `/remove`                       | Set only under fresh existing-method authorization and verified stored email; never anonymous reset of an unconfigured password. Removal cannot strand user without another configured independent sign-in method.                     |
| `POST /api/auth/google/link`                                              | Fresh operation grant plus a new link-purpose Google nonce/token; handle revoked identity rows explicitly without creating duplicates.                                                                                                 |
| Existing security list/unlink/revoke and email recovery endpoints         | Apply last-method checks, TOTP-aware recovery policy, invalidation, and operation-specific grants.                                                                                                                                     |

Persist authentication metadata through Passport serialization: `authenticationMethod`, `secondFactor` (nullable), `authenticatedAt`, `authVersion`, and selected account. Do not label Google as `totp`, `email`, or confirmed MFA. Interpret a legacy session without `authVersion` as version 1 only while the current user's version is exactly 1; never populate a missing session version from the current user version. Such sessions retain only their existing ordinary authority and must explicitly reauthenticate for security changes. After any version increment, reject them in HTTP and realtime just like other stale sessions. If that compatibility rule cannot be enforced in every consumer, expire legacy sessions at rollout rather than exempting them.

## 3. Alternatives

- **ALT-001**: Passkey plus Google only was rejected because unsupported/inconvenient credential environments and users without Google need an independent access path.
- **ALT-002**: Google-first ordering was rejected; Google is sufficient but passkey remains preferred.
- **ALT-003**: Mandatory TOTP for every password user was rejected. Email code is the selected second step until an authenticator is confirmed.
- **ALT-004**: Email code fallback for enrolled TOTP was rejected because it defeats the stronger enrollment, including through password reset or passkey recovery.
- **ALT-005**: Email-only routine sign-in was rejected. Email login proof must follow correct password proof; email-only recovery is separate, lower assurance, constrained, and unavailable as a TOTP bypass.
- **ALT-006**: Identifier-first routing for every visit was rejected for the initial release. The conventional template makes available methods explicit without a method-discovery wizard.
- **ALT-007**: Auto-linking Google by email, automatic passkey creation, SMS, trusted-device code bypass and a new mail queue were excluded to keep this release bounded.
- **ALT-008**: Replacing the backend with an external auth platform is not part of this plan. Reuse existing session, WebAuthn, Google and mail boundaries; use maintained libraries for new cryptographic operations.

### Acceptance Scenarios

- **TEST-001**: New password user verifies email once, gains full access, logs out, and returns through password plus a fresh email code. No passkey/Google/extension is needed.
- **TEST-002**: Correct password alone, pending signup, pending reset and pending factor sessions cannot access protected HTTP endpoints, issue API keys, activate workspaces, register credentials or establish authenticated realtime access.
- **TEST-003**: Confirmed TOTP selects authenticator verification and sends no email; invalid/missing/decryption-failed TOTP cannot request email. Pending setup does not count as enrollment. Enrollment during an email flow invalidates that flow.
- **TEST-004**: Email code and reset/recovery tokens reject wrong purpose, wrong user, wrong browser, expired/superseded/consumed proof and replay. Resend does not renew password-proof lifetime or replenish attempt counts. Concurrent submissions permit only one success.
- **TEST-005**: TOTP accepts the documented window, rejects replay atomically and locks the flow after its attempt budget. Recovery codes preserve leading format characters, are single-use, are not logged and become invalid after regeneration.
- **TEST-006**: Password reset preserves TOTP and requires normal login afterward. Email recovery cannot enroll a new passkey or disable TOTP for enrolled users. Unsupported/unconfigured password requests do not create a password without authorized method setup.
- **TEST-007**: Passkey and linked Google logins require no local code. Wrong Google issuer/audience/nonce, expired token, unverified email, replayed completion and unlinked-email collisions fail safely. Google success UI never says `Passkey verified`.
- **TEST-008**: A Google-only or passkey-only user can explicitly add password under fresh authorized proof; a password/Google user can add a first passkey without already having one. Google linking requires fresh account proof and a link-purpose provider token.
- **TEST-009**: Multiple registered passkeys enter the same global user with correct credential-bound tenant authority. New unregistered credentials never claim ownership by email. Removing methods concurrently cannot remove the last usable independent sign-in method.
- **TEST-010**: Fresh and upgraded durable databases preserve password hashes, passkey state/public keys, federated subjects and memberships. Legacy verified passwords upgrade only after successful verification. Race slow legacy verification against reset/change/removal and assert compare-and-swap cannot overwrite a newer credential or restore the old password. Null/unsupported hashes do not become blank/default passwords.
- **TEST-011**: Password and TOTP/reset changes invalidate relevant sessions and pending grants; serialization retains actual method/factor/account/version. Create a pre-migration session without metadata, increment the user's version through reset/factor change, and reject subsequent HTTP and realtime access. Unknown old-session metadata cannot authorize sensitive actions. No session fixation or unsafe return URL. Disabled capabilities reject direct API calls; disabling TOTP enrollment never disables verification for enrolled users.
- **TEST-012**: Email outage, Redis outage, Google SDK/CSP failure, passkey cancellation, no provider, expiry, refresh, Back and multiple tabs produce safe recoverable UI without authentication bypass. Mail resend after failure respects delivery/attempt budgets.
- **TEST-013**: Password/TOTP/email work in Firefox/Linux clean profile and Chromium; production Google is verified separately from mocked browser tests. Supported passkey manager/hardware and real Apple/browser configurations have recorded evidence, not inferred capability claims.
- **TEST-014**: Approved snapshots cover all states, mobile/desktop and light/dark. Keyboard, focus, screen-reader names, AXE, paste/autofill, password visibility, localized copy, and safe public links work. Source artifact remains unchanged.

## 7. Risks & Assumptions

- **RISK-001**: Email two-step verification and email password reset share a trust boundary. A compromised mailbox can defeat the no-TOTP password branch via reset plus code. This is an accepted coverage/usability tradeoff, not equal assurance to TOTP or a UV passkey.
- **RISK-002**: Google is accepted independently of local TOTP. An enrolled authenticator does not protect against compromise of an already linked Google identity under this policy. Per-tenant mandatory assurance is outside scope and must not be implied.
- **RISK-003**: Existing email recovery and generic restricted authorization are potential indirect bypasses. The password feature cannot ship until those paths enforce the new policy.
- **RISK-004**: Physical databases may retain legacy password columns/data absent from the current ORM schema. A naive generated migration can destroy credentials or revive unsupported hashes. PH-01 inventory and PH-03 preservation tests are release gates.
- **RISK-005**: Loss of TOTP encryption keys locks out enrolled password users; silent email fallback is prohibited. Backups, versioned rotation and independent configured methods/recovery codes are required.
- **RISK-006**: Users losing TOTP, recovery codes and all independent methods cannot self-recover in this release. Explain this during enrollment; do not promise an unimplemented support bypass.
- **RISK-007**: Existing source tests/specs are partially stale; green historical snapshots and completed old plan rows do not validate new flows. Record and repair baseline drift rather than skipping tests/hooks.
- **RISK-008**: Argon2 cost and distributed limits can affect latency/availability, especially behind shared IPs. Benchmark and observe staging data; changes to thresholds require documented plan/config updates, not frontend-only workarounds.
- **RISK-009**: Rollback to old auth code can create a security downgrade or strand newly created password-only users. Preserve enforcing backend behavior and new credential storage during rollback.
- **ASSUMPTION-001**: The user approved the three-method direction, supplied template reference, and email second step when no authenticator is linked. Detailed defaults and recovery restrictions here are implementation recommendations; any changed decision requires a versioned update.
- **ASSUMPTION-002**: This is a plan-only change. No schema mutation, dependency installation, work-item activation, commits, deployment or application implementation is authorized by writing the guide.
- **ASSUMPTION-003**: Existing same-user memberships and encrypted-data recovery remain separate from login authority. Restoring account access does not promise recovery of independently encrypted data.
