# Vault and Cloud examples

Use synthetic notes and accounts in your demo workspaces.

| Example                                              | Where data lives                                                                                                                                                                                       | Who can read it                                                                                                                                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Vault with synchronization** (`/db-example/vault`) | A new test note starts in IndexedDB. An automatic backup stores its encrypted envelope in private S3-compatible storage. PostgreSQL stores opaque references, versions, integrity and access metadata. | A device with a usable key can read its local copy. Access to the workspace and signed device authorization are required to download the backup.                                          |
| **Cloud** (`/db-example/cloud`)                      | Notes go directly to PostgreSQL through the SaaS records API.                                                                                                                                          | The owner can create, read, edit, and delete notes. An explicitly permitted test account can read shared notes. Trusted services and database administrators can read the stored content. |

Stack offers two persistence modes. Use Cloud for service-readable data and account-based collaboration. Use Vault for client-encrypted data synchronized across approved devices. IndexedDB holds each device’s encrypted copy and pending changes within the synchronized Vault. Cloud access uses a verified account session, resource grants, and PostgreSQL row-level security (RLS). Cloud is service-readable SaaS storage and makes no zero-knowledge claim.

## Example routes and storage availability

Normal authentication registers the Example domain in development, test and production modes. The localized client routes are `/app/{en,es}/db-example/vault` and `/app/{en,es}/db-example/cloud`. The gateway mounts the API at `/api/example/vault` and `/api/example/cloud`. The standalone API serves the same routers at `/example/vault` and `/example/cloud` from its root. Both require a current verified full session, even for the policy probes. The former API namespace `/persistence` and the flattened example slugs have no API aliases.

The `/app/{en,es}/db-example` page is the technical hybrid harness for route isolation, offline sync and pairing regression tests. It uses the new Vault API and requires `NODE_ENV=development` or `NODE_ENV=test`, `VISOMI_PERSISTENCE_EXAMPLE=true`, and `VISOMI_PERSISTENCE_DEMOS=true`. Its server-readable operations and ability to create inline test workspaces are gated to that profile. The regular Vault example creates object-backed resources only.

New backups require a private S3-compatible bucket with these server-only settings.

- `PRIVATE_S3_ENDPOINT` is the base HTTPS origin. Use `https://t3.storageapi.dev` for Railway's virtual-host buckets. The server signs requests to the exact `<bucket>.t3.storageapi.dev` origin with region `auto`. Other endpoints use path-style requests signed for `us-east-1`. Development and tests also accept HTTP on `127.0.0.1`.
- `PRIVATE_S3_BUCKET` identifies the private bucket.
- `PRIVATE_S3_ACCESS_KEY` and `PRIVATE_S3_SECRET_KEY` authorize the server to read and create backup objects and delete abandoned uploads under `vault-backups/`.

Missing or unsafe storage configuration prevents setting up a new backup workspace. An already enrolled device can still unlock its existing encrypted copy when the session and local custody allow it. Previous workspaces keep their PostgreSQL ciphertext history and access rules. The tests start a pinned disposable SeaweedFS container with synthetic credentials. The API integration uses path-style URLs. The authenticated browser fixture forwards Railway-style signed requests to that local server while preserving the signed host and object path.

The [Railway IaC definition](../.railway/railway.ts) declares the `private-files` bucket and references its credentials from the gateway. Vault uses the `vault-backups/` prefix within that bucket. PostgreSQL persists backup references and authorization metadata on its own volume.

Private user files must be encrypted before upload with keys bound to the user's authorized private scope. The bucket stores ciphertext, and each use of the bucket must authorize access to its own scope. Vault already follows this rule for its backups. The current Example API supports Vault envelopes.

Initialize Cloud RLS once after the standard persistence migrations. The authenticated Playwright fixture provisions an isolated PostgreSQL 16 cluster and applies the [Cloud RLS setup](../libs/backend/db/tools/cloud-example-rls.sql) automatically. For a manual run in an equivalently isolated profile, use the fixture database login that owns the tables and that the synthetic API connects as.

```sh
psql "$SYNTHETIC_EXAMPLE_DATABASE_URL" -X -v ON_ERROR_STOP=1 -f libs/backend/db/tools/cloud-example-rls.sql
```

On a deployed Stack database, an operator provisions the same policies after checking that the intended database has the standard persistence tables and that the restricted role and policies are absent. The setup grants the invoking login permission to switch roles. Verify that this is the login used by the deployed gateway, that it can switch to `visomi_cloud_example_records`, and that `row_security_active` returns true for both persistence tables in that role.

## Reopen an existing workspace

Open **Cloud example** from the authenticated menu. The workspace list shows workspaces you own or have permission to read. Choose a workspace to see its notes, or use its direct link. If access is revoked, the workspace is removed from the next list and its direct link is denied.

Open **Vault example** from the menu and choose the existing vault. The list uses the signed-in account to find accessible backup workspaces. The vault still needs a linked device and explicit unlock to open its encrypted note. Reloading keeps the note address and locks the vault. If you need to sign in again, the app returns to that address so you can unlock the same vault.

The list includes a Vault Example workspace once the server has committed the initial device registry. A vault with no saved note is ready to open. Canceling setup or interrupting its first device registration leaves a reservation accessible through **Continue vault setup**. The owner can retry the same workspace with the original local unlock method. Setup can resume after device custody was partially stored. A new browser without local custody links to the completed vault through device approval.

## Try Cloud sharing

1. Sign in to one test account, open **Cloud example**, and create a workspace. Save an owner-only note and a shared note with synthetic content.
2. Open **Share workspace** as the owner. Choose **Share by email** to grant a verified test account read access and send its workspace address. Choose **Share by link** to create a seven-day link that a signed-in, verified account can redeem. Open the invitation in a separate browser profile.
3. Open the workspace with the reader. Only the shared note appears. Edit the shared note as the owner and verify that the reader sees the change without reloading. Try the same address in a third, unrelated profile to see access denied.
4. Open **People with access** as the owner and remove the reader. The reader’s screen automatically clears its notes, and the reader cannot use the link to rejoin. Disabling or replacing the link stops future joins through that link. Current readers keep their grants until removed.

Sharing links contain a random token in the URL fragment. PostgreSQL stores only its hash and expiration. Redeeming a link requires a verified session and grants read access through the same membership, grant, and RLS rules as email sharing. The email contains the workspace address and does not carry an access token. If delivery fails after the grant commits, Cloud reports that the account has access and lets the owner retry sending.

Cloud sends a payload-free hint over the existing authenticated session channel after a note or permission change commits. Only the affected accounts receive the hint. The browser refetches through the regular Cloud API and rechecks permissions, including RLS. Reconnecting the session channel also refetches the open view. A browser reload reads the current state if realtime is temporarily unavailable. The Cloud routes open directly even when the same browser has a locked Vault.

The API derives the actor from the verified session and checks membership, resource grants, and record rules. The Cloud product uses its own resource scopes in the existing persistence tables. For record operations, the API switches its transaction to `visomi_cloud_example_records`, a non-owning, non-superuser role without `BYPASSRLS`, and sets the server-derived account and scope as transaction-local context. PostgreSQL checks active membership, the explicit reader grant, and each record’s owner/audience. Policies also constrain record writes and idempotency receipts. The transaction uses the same tenant lock as grant changes. Notes older than 90 days are hidden. When the owner creates a note, the same transaction clears expired content and reclaims its capacity under that restricted role. If the role is missing or RLS is inactive, CRUD fails closed. The standard pool still handles sessions and grant administration. RLS constrains the effective record role and complements the application’s authorization. The database and trusted runtime retain access to plaintext.

## Back up and restore a Vault note

1. On **Vault example**, select **Set up my vault**. Use a passkey already registered to your account or explicitly choose a local PIN when PRF is unavailable. Type a synthetic note. Setup creates a private resource in the existing authorized `private-resources` scope.
2. After a short pause in typing or when the editor loses focus, the browser automatically encrypts the edit and starts its backup. Before upload, the encrypted note is stored in IndexedDB’s outbox. The opaque replica sends that same envelope in a signed request. The API selects the object key from the authorized resource and a fresh opaque ID, writes the immutable object and reads it back. It commits the reference and the history update only after the bytes match. The replica clears the outbox after it verifies the committed write.
3. Open the workspace address in a fresh profile signed in to the same test account. Choose **Link a device** and request pairing. In the first profile, choose **Review request** on the in-app notice or open the review link from the new profile. Unlock the first profile if needed. Enter the fingerprint shown on the new profile and explicitly approve. Wait for the approval on the new profile, then finish with the fingerprint shown on the approver.
4. Select **Open vault note** to return to the same Vault workspace. The first restore starts automatically when the paired workspace opens. The recipient verifies the encrypted history and stores the same encrypted note in IndexedDB before showing its content. After reloading, unlock the paired profile to read its local copy.

Vault Example uses an authenticated socket hint to refresh pending requests and approval status. Visible tabs recheck over HTTP when they resume and when a socket is disconnected. The review link identifies a scoped, five-minute request. The server verifies the recipient's signed proof before listing the request, and the two browsers still compare the fingerprints directly before delivering and installing the data key.

Initial Vault Example setup obtains the active WebAuthn credential IDs for the verified account from `GET /api/auth/passkeys/vault-credentials`. This endpoint returns only those IDs and is served with `Cache-Control: no-store`. The browser performs a user-verified WebAuthn assertion scoped to those IDs and the configured RP, and checks the returned ID against the account’s list before writing local wrappers. New account passkey registrations request PRF support without evaluating it. Passkey sign-in accepts credentials with or without PRF. A credential registered before this change can still be used when its assertion returns PRF. An assertion without PRF offers the explicit PIN option. If the account has no registered passkey, the setup action points to passkey management in Security. Canceling the picker leaves setup retryable.

The browser asks for the resource and device PRF outputs in one assertion. If the authenticator returns only the first output, setup obtains the second in a separate assertion before saving either wrapper. Both outputs stay in the browser and are consumed only by their original wrappers. Previously configured vaults use their stored credential or PIN, including dedicated vault credentials created by older versions. A new browser profile still requires approved device pairing, which has its own enrollment flow. A desktop can use the browser’s nearby-phone passkey option when supported, or pair using its own PIN after confirmed PRF unavailability. The vault locks after five minutes without interaction, on page exit, and when the account session ends. The account menu also offers immediate locking. [WebAuthn PRF extension](https://www.w3.org/TR/webauthn-3/#prf-extension).

Object-backed requests check the current account and private scope. The existing signed `sync` action authorizes each pull against the current device roster and the verified session. The recipient still needs the approved device delivery to decrypt the note. The bucket stays private. The API reads the object server-side and checks its size, SHA-256 digest and envelope version before returning it. A prefix provides organization. Scope and device checks provide authorization. Plaintext, raw decryption keys, the PIN, and PRF output stay in the browser. The server uses the MIT-licensed S3 Lite Client’s public signing API and sends the short-lived signed request through native fetch. Credentials and signed URLs stay on the server. Fetch rejects redirects and aborts on a four-second deadline that also covers streamed reads.

The browser verifies every page through one pinned head before committing it to IndexedDB. It waits and retries the current request on a rate limit, keeping verified pages in memory until the final transaction. A missing, truncated or corrupt object aborts the restore and keeps existing local data and the pending encrypted outbox. Existing PostgreSQL retention and replay fences still apply. Losing all usable keys can permanently lose access to the backup workspace.

After the first verified restore, an unlocked object-backed workspace can receive live updates through the existing realtime gateway. The socket subscription uses a device proof tied to the current account session and the exact private resource. Each delivery rechecks access, pairing, generation and revocation. A committed upload sends only a cursor to that resource’s approved subscribers. Each browser independently checks and restores the opaque history through its authorized HTTP pull. A draft or pending upload defers incoming changes. After unlock or network reconnection the browser retries the existing signed outbox before pulling. The editor is read-only while a verified read or publication is in progress. Offline changes that have reached IndexedDB survive a reload. Unlocking or reconnecting checks for missed updates from the local pin. The header reflects the actual pull or upload, and offers a retry if it fails. Notifications are best effort. Progress and retry feedback use a compact header indicator and a polite status announcement that keeps focus in the editor. [W3C guidance on status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

The API commits one staging reservation per workspace before attempting a write. A retry of the same signed operation uses the same object key. Verifying the object, publishing its reference and clearing the reservation preserve the previous valid references if the database transaction rolls back. After the reservation expires, the next upload or the owner’s Vault maintenance endpoint can delete its abandoned object. Failed deletion leaves the reservation in place and blocks allocation of another staged object for that workspace. Use an unversioned demo bucket so object deletion releases the stored bytes. Bucket versioning and provider retention can retain copies independently of application cleanup. Maintenance only sees tracked reservations. Older untracked objects require an independently verified inventory before any cleanup. The disposable fixture clears its bucket at teardown.

The [authenticated browser test](../apps/web/app-e2e/auth/vault-object-backup.auth.spec.ts) compares the original outbox envelope with the upload, the stored object and restored IndexedDB bytes. It checks reference-only PostgreSQL rows, same-account and unrelated-account denial, retry after a truncated download, a live update in a second profile without navigation, draft protection, a missed update while locked, and the fixed-size sync indicator. It uses Chromium and a virtual authenticator for recipient PRF. The [Vault setup tests](../apps/web/app-e2e/auth/vault-demo.auth.spec.ts) cover explicit PIN setup and reopen in Chromium, Firefox and WebKit. Chromium also covers reuse of the signup credential without increasing the authenticator’s credential count, rejection of a different account’s credential at the same RP, and cancellation. The no-PRF tests cover a passkey registered using the older options on a PRF-capable authenticator and a new passkey on an authenticator without PRF.

The Chromium virtual-passkey test hard reloads Vault Example after verified signup, before setup and after canceling the picker. On the baseline merged from PR #44 (`463ab0b`), the synthetic browser retained its session cookie, SSR rendered the Vault route with full access, and the session endpoint confirmed a verified account. No login redirect was reproduced with a full session. The anonymous and expired session controls redirected to sign-in with a safe return address, and passkey sign-in returned to the same unconfigured workspace.

Physical iPhone Safari validation is pending. Start with the existing account and passkey before validating fresh signup. The account holder can perform the check without resetting credentials or browser data. ### Configured vault reload and unlock

The tests start with a synthetic account and a saved note. They open the configured vault with its existing passkey or PIN before reloading the protected document. On the merged baseline `bedc97b`, the browser retained its session cookie and the first response with a valid session was HTTP 200. SSR rendered the authenticated shell with full access. Hydration revalidated the session with HTTP 200, and a separate browser request confirmed full and verified access. The Vault policy request followed the document response. That baseline displayed an unlock card inline. The reported sign-in redirect did not reproduce. [Configured Vault reload tests](../apps/web/app-e2e/auth/configured-vault-reload.auth.spec.ts).

The gateway resolves session context before Angular renders the document. The authenticated route runs the full-session guard before activating Vault Example. After browser rendering, a configured local binding that needs unlocking opens the localized page at `/vault/unlock` within the authenticated shell. The route carries three validated workspace identifiers. Canceling stays on that page. Explicit unlock returns to the canonical note URL for those same identifiers. A session that expires or is absent first receives HTTP 302 to sign-in with that canonical return path. [Gateway](../apps/web/gateway/src/app.ts), [Vault routes](../apps/web/app/src/app/db/example/vault/vault-routes.ts), [Vault workspace](../apps/web/app/src/app/db/example-workspace.ts).

The fixture uses loopback HTTP, virtual Chromium PRF, and real PIN wrapping in Playwright Chromium, Firefox and WebKit. The iPhone Safari session-loss report still needs physical evidence. A first document returning HTTP 302 would identify a server-side redirect, while HTTP 200 with full SSR access followed by sign-in would place the transition after that response. Share only status, route type, session classification and cookie-presence booleans from a physical check.

On the PR #47 baseline (`1e89b7f9`), the fixture also reloaded a configured vault while locked, immediately after explicit unlock, and on Home after navigating there from an open vault. In all three ordinary reloads the first document returned HTTP 200 without a redirect, SSR transferred full verified access, and the first session fetch during hydration confirmed full verified access with HTTP 200. The session cookie was present in the browser's cookie jar. Reloading the open note locked it and showed the dedicated unlock page. Reloading Home stayed on Home. Expired and anonymous Home controls received HTTP 302 with a safe Home return path and then hydrated with anonymous access. The physical post-unlock redirect remains unexplained.

Combining ordinary reloads, a hard reload and an offline check in one rapid PIN test also produced HTTP 429 on Home's hydration request after HTTP 200/full on the document. The browser remained on Home in that observation. The regression suite exercises these journeys with separate accounts so their requests do not accumulate across scenarios.

The sign-in screen has three distinct actions relevant to a one-click return. **Continue** can use a session already verified on focus. **Try again** retries an unavailable session read. **Sign in with a passkey** starts a WebAuthn assertion and submits it for verification. The [sign-in controls](../apps/web/app-e2e/auth/access.auth.spec.ts) exercise the first two separately with a valid session. The expired Vault control exercises the third with a virtual authenticator.

If the redirect recurs on an iPhone, the most useful observations are the iOS version, the screen immediately before reload (locked Vault, open note or Home), the exact button label on return, and whether a system passkey dialog appeared. If Web Inspector is available, record the first document status and destination category, whether the return path denotes Home or Vault, and the status and access classification of the first session response. Cookie presence can be recorded as a boolean. These observations require no account identifiers, full addresses or credential values.
