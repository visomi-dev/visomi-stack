# Vault and Cloud examples

Use synthetic notes and accounts in your demo workspaces.

| Example                                            | Where data lives                                                                                                                                                                                      | Who can read it                                                                                                                                                                           |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Vault local download** (`/example/vault`)        | The original sample is encrypted in this browser’s IndexedDB. The optional file contains its ciphertext and the primary device-bound wrapped key.                                                     | A signed-in user must unlock the local vault using its configured PIN or verified passkey PRF.                                                                                            |
| **Vault backup test workspace** (`/example/vault`) | A new test note starts in IndexedDB. An explicit upload stores its encrypted envelope in private S3-compatible storage. PostgreSQL stores opaque references, versions, integrity and access metadata. | A device with a usable key can read its local copy. Access to the workspace and signed device authorization are required to download the backup.                                          |
| **Cloud** (`/example/cloud`)                       | Notes go directly to PostgreSQL through the SaaS records API.                                                                                                                                         | The owner can create, read, edit, and delete notes. An explicitly permitted test account can read shared notes. Trusted services and database administrators can read the stored content. |

Choose Cloud for service-readable data and account-based collaboration. Use the Vault example to see browser-local encryption and the separate unlock step. Cloud access uses a verified account session, resource grants, and PostgreSQL row-level security (RLS). Cloud is service-readable SaaS storage and makes no zero-knowledge claim.

## Example routes and storage availability

Normal authentication registers the Example domain in development, test and production modes. The localized client routes are `/app/{en,es}/example/vault` and `/app/{en,es}/example/cloud`. The gateway mounts the API at `/api/example/vault` and `/api/example/cloud`. The standalone API serves the same routers at `/example/vault` and `/example/cloud` from its root. Both require a current verified full session, even for the policy probes. The former API namespace `/persistence` and the flattened example slugs have no API aliases.

The remaining `/app/{en,es}/persistence` page is the technical hybrid harness for route isolation, offline sync and pairing regression tests. It uses the new Vault API and requires `NODE_ENV=development` or `NODE_ENV=test`, `VISOMI_PERSISTENCE_EXAMPLE=true`, and `VISOMI_PERSISTENCE_DEMOS=true`. Its server-readable operations and ability to create inline test workspaces are gated to that profile. The regular Vault example creates object-backed resources only.

New backups require a private S3-compatible bucket with these server-only settings.

- `VISOMI_VAULT_BACKUP_S3_ENDPOINT` is the fixed HTTPS origin for path-style requests signed for `us-east-1`. Development and tests also accept HTTP on `127.0.0.1`.
- `VISOMI_VAULT_BACKUP_S3_BUCKET` identifies the private bucket.
- `VISOMI_VAULT_BACKUP_S3_ACCESS_KEY` and `VISOMI_VAULT_BACKUP_S3_SECRET_KEY` authorize the server to read and create backup objects and delete abandoned uploads under `vault-backups/`.

Missing or unsafe storage configuration leaves new Vault backups unavailable while the local Vault stays available. Previous workspaces keep their PostgreSQL ciphertext history and access rules. The authenticated tests start a pinned disposable SeaweedFS container with synthetic credentials. The production-mode support is tested in isolation.

Run the [Cloud RLS setup](../libs/backend/db/tools/cloud-example-rls.sql) once after the standard persistence migrations, on a freshly provisioned, isolated PostgreSQL 16 test cluster. Apply it with the fixture database login that owns the tables and that the synthetic API connects as. The script grants that login permission to switch to one restricted role. The authenticated Playwright fixture provisions its own database and applies the script automatically. For a manual run in an equivalently isolated profile, run the following against the disposable test database.

```sh
psql "$SYNTHETIC_EXAMPLE_DATABASE_URL" -X -v ON_ERROR_STOP=1 -f libs/backend/db/tools/cloud-example-rls.sql
```

## Try Cloud sharing

1. Sign in to one test account, open **Cloud example**, and create a workspace. Save an owner-only note and a shared note with synthetic content.
2. Sign in to a different verified test account in a separate browser profile. Copy its test account ID from the Cloud screen. As the owner, grant that ID read access to the workspace, then send its address to the permitted account. The address carries no permission.
3. Open the workspace with the reader. Only the shared note appears. Try the same address in a third, unrelated profile to see access denied.
4. Remove the reader’s access as the owner. Refresh on the reader’s screen to see access denied. Previously viewed content could already have been copied.

The API derives the actor from the verified session and checks membership, resource grants, and record rules. The Cloud product uses its own resource scopes in the existing persistence tables. For record operations, the API switches its transaction to `visomi_cloud_example_records`, a non-owning, non-superuser role without `BYPASSRLS`, and sets the server-derived account and scope as transaction-local context. PostgreSQL checks active membership, the explicit reader grant, and each record’s owner/audience. Policies also constrain record writes and idempotency receipts. The transaction uses the same tenant lock as grant changes. Notes older than 90 days are hidden. When the owner creates a note, the same transaction clears expired content and reclaims its capacity under that restricted role. If the role is missing or RLS is inactive, CRUD fails closed. The standard pool still handles sessions and grant administration. RLS constrains the effective record role and complements the application’s authorization. The database and trusted runtime retain access to plaintext.

## Download the local Vault sample

1. Open **Vault example**, set up or unlock the local vault, and open the synthetic note. If you have no eligible credential, choose **Create a vault passkey** after the first attempt and verify it on this device. A cancelled passkey prompt can be retried. The local PIN option appears when passkey PRF is unavailable.
2. Choose **Download encrypted backup**. The browser exports the exact stored encrypted note and its original wrapper. It sends no backup payload to the API. Keep the file private. A PIN-protected copy permits offline PIN guessing. A passkey added later to a PIN vault is a local secondary wrapper and is outside the current backup format.
3. Open the same Vault URL in a fresh profile signed in to the same account. That profile still needs its own vault setup and does not see the original note. The download provides no authorized import on that profile.

The v1 file restore SDK requires a trusted expected owner, device, origin, unlock method and scope, plus an independent generation floor. Import into empty storage stays locked until the recipient proves custody, and the restored generation is read-only. The local reference vault has no server roster, enrollment authority, or recipient binding. The exported wrapper is bound to the source device. Copying that binding into a new profile would make the recipient impersonate the source. Account login and possession of the file supply neither the trusted generation nor recipient custody. The local download stays in the browser.

## Back up and restore a new Vault test note

1. On **Vault example**, under **Back up and restore a test note**, create a backup test workspace. Set up its first device and save a synthetic note. This creates a new private resource in the existing authorized `private-resources` scope. The original local sample keeps its own keys and ciphertext.
2. Choose **Upload encrypted note**. Before upload, the encrypted note is stored in IndexedDB’s outbox. The opaque replica sends that same envelope in a signed request. The API selects the object key from the authorized resource and a fresh opaque ID, writes the immutable object and reads it back. It commits the reference and the history update only after the bytes match. The replica clears the outbox after it verifies the committed write.
3. Open the workspace address in a fresh profile signed in to the same test account. Signing in alone leaves the note locked. Open **Vault devices** in both profiles and request pairing on the new profile. Compare the fingerprints directly and approve from the unlocked first device. Finish with the verified approver fingerprint on the new profile.
4. Select **Open test private resource** to return to the same Vault workspace. Choose **Download and restore note**. The recipient verifies the encrypted history and stores the same encrypted note in IndexedDB before showing its content. After reloading, unlock the paired profile to read its local copy.

Object-backed requests check the current account and private scope. The existing signed `sync` action authorizes each pull against the current device roster and the verified session. The recipient still needs the approved device delivery to decrypt the note. The bucket stays private. The API reads the object server-side and checks its size, SHA-256 digest and envelope version before returning it. A prefix provides organization. Scope and device checks provide authorization. Plaintext, raw decryption keys, the PIN, and PRF output stay in the browser. The server uses the MIT-licensed S3 Lite Client’s public signing API and sends the short-lived signed request through native fetch. Credentials and signed URLs stay on the server. Fetch rejects redirects and aborts on a four-second deadline that also covers streamed reads.

The browser verifies every page through one pinned head before committing it to IndexedDB. It waits and retries the current request on a rate limit, keeping verified pages in memory until the final transaction. A missing, truncated or corrupt object aborts the restore and keeps existing local data and the pending encrypted outbox. Existing PostgreSQL retention and replay fences still apply. The original local file remains tied to its source device. Losing all usable keys can permanently lose access to the backup workspace.

The API commits one staging reservation per workspace before attempting a write. A retry of the same signed operation uses the same object key. Verifying the object, publishing its reference and clearing the reservation preserve the previous valid references if the database transaction rolls back. After the reservation expires, the next upload or the owner’s Vault maintenance endpoint can delete its abandoned object. Failed deletion leaves the reservation in place and blocks allocation of another staged object for that workspace. Use an unversioned demo bucket so object deletion releases the stored bytes. Bucket versioning and provider retention can retain copies independently of application cleanup. Maintenance only sees tracked reservations. Older untracked objects require an independently verified inventory before any cleanup. The disposable fixture clears its bucket at teardown.

The [authenticated browser test](../apps/web/app-e2e/auth/vault-object-backup.auth.spec.ts) compares the original outbox envelope with the upload, the stored object and restored IndexedDB bytes. It checks reference-only PostgreSQL rows, same-account and unrelated-account denial, a truncated download, and a local reopen after successful restore. It uses Chromium and a virtual authenticator for recipient PRF. WebKit coverage of the original local Vault uses simulated WebAuthn. Physical iPhone Safari has not been verified.
