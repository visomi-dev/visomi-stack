## High Priority

### 1. Docker build — PNPM config / version mismatch

**Status: FIXED in code (pending CI re-run)**

- Evidence: GitHub check `Docker / build`, run `25697471600`, job `75449253770` failed at `Dockerfile:35`
  on `pnpm install --frozen-lockfile --prod`.
- Root cause: `Dockerfile:33` was copying only `package.json` + `pnpm-lock.yaml` and `pnpm-workspace.yaml`
  (with the `allowBuilds` config) was missing. PNPM was also unpinned (`corepack enable` alone).
- Fix applied:
  - `Dockerfile:33` now includes `pnpm-workspace.yaml` in every install COPY.
  - `Dockerfile:7` pins PNPM via `corepack prepare pnpm@10.2.1 --activate`, matching CI.
- **Pending:** push to branch to trigger a new Docker build check in CI.

### 2. API e2e auth fails with secure cookies

**Status: FIXED**

- `apps/web/api-e2e/src/support/global-setup.ts:20-31` now explicitly overrides:
  ```
  COOKIE_SECURE: 'false',
  NODE_ENV: 'test',
  ```
  The test server no longer inherits the host environment's secure-cookie config.

### 3. SSR API requests target wrong port

**Status: FIXED**

- `apps/web/app/src/app/shared/http-interceptor.ts` no longer hard-codes `internalApiUrl`.
  It now dynamically derives the API origin from the `REQUEST` object:
  - Parses the full URL if available.
  - Falls back to `protocol://host` from request headers.
- The static `environment.internalApiUrl` is only a fallback when no `REQUEST` is available.

### 4. Activation guard not applied to protected routes

**Status: FIXED**

- `activatedGuard` (now at `activated.guard.ts`) is imported in `app.routes.ts:6` and applied
  to `/dashboard`, `/projects`, `/projects/new`, and `/projects/:id` alongside `authenticatedGuard`.
- Guard file renamed to follow `.guard.ts` convention.

## Medium Priority

### 1. Repeated password sign-in may not resend the code

**Status: FIXED**

- `apps/web/api/src/auth/auth-service.ts:222` now calls `createChallenge(user, 'sign_in')` instead of
  `getOrCreateActiveChallenge`. The comment at lines 220-221 explicitly documents the intent:
  "Always generate a fresh verification challenge to ensure a fresh email code is sent and any previous
  unconsumed sign-in challenges are invalidated."
- Sign-up (unverified email) still reuses challenges via `getOrCreateActiveChallenge` at line 211,
  which is intentional — the user hasn't verified their email yet and a single active challenge suffices.

### 2. Authenticated users can open sign-in route directly

**Status: FIXED**

- `apps/web/app/src/app/app.routes.ts:27-31` now applies `canActivate: [anonymousGuard]` to `/sign-in`,
  matching sign-up and forgotten-password behavior.

### 3. Unused REQUEST injection in auth service

**Status: FIXED**

- `apps/web/app/src/app/shared/auth/auth.ts:3,28` now imports and injects `REQUEST_CONTEXT` instead of
  `REQUEST`. The `requestContext` is used in `ensureSessionLoaded()` (line 49) for SSR user hydration.
